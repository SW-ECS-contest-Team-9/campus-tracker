계획과 달라진 점:

- **대표 경로 파라미터:** 합성 격자 탐색으로 법선 방향 ±5 m 현, 이동 중앙값 7점, 최대 8회 반복으로 정했다. 독립 잡음 5회에서 대표 경로 오차는 회차 오차의 0.53~0.60배다(5개 중앙값의 이론값 0.56). 그래서 테스트 기준은 0.6배가 아니라 0.7배로 잡았다.
- **신뢰 폭:** 반폭 = 2·√(σ² + se²)로, 새 회차에 대한 예측 폭이다. σ는 모든 표로 계산한다(MAD는 이미 강건하므로, 이상치를 뺀 뒤 다시 재면 이중으로 좁아진다). 합성 경로의 회차 빼기 포함률은 79%에서 83%가 됐다.
- **회차 투표:** 각 점의 횡오프셋은 ±5 m 현으로 다듬은 법선 방향으로 잰다. 이웃 1 m 점으로 법선을 구하면 노이즈 때문에 방향이 크게 흔들려 진행 방향 오차가 섞였다(검증 비율이 1.0을 넘음).

핵심 판단:

1. **방향은 맞다.** 같은 길을 여러 번 걸어 대표 경로와 신뢰 폭을 만들고 수치로 검증하는 흐름은 지금 단계에 적합하다. 이미 있는 것은 재사용한다. 실시간과 같은 엔진으로 하는 재처리, 버전별 저장, 지형 Z 영점, v4 이상치 게이트, 마커가 여기에 해당한다.
2. **실제로 빠진 것은 네 가지다.**
   - 같은 버전을 다시 돌리면 이전 결과가 지워져 수정 전/후를 비교할 수 없다.
   - 엔진 좌표의 원점이 세션마다(첫 GPS) 달라, 세션끼리 미터 단위로 비교할 공통 좌표가 없다.
   - 여러 세션을 '같은 경로의 회차'로 묶는 계층이 없다.
   - 정답 기준(위치를 아는 지점)이 없다.
3. **합성 데이터(19)를 1묶음으로 당긴다.** DB의 23개 세션 중 같은 길을 겹쳐 걸은 것은 3개뿐이다(813468d0·fbaa781d·e54010c2, 북악관 진입로). 반복 측정 알고리즘은 정답을 아는 합성 회차로 먼저 검증해야 한다.
4. **재생 속도(1x/5x/20x)는 화면에서 처리한다.** 엔진은 결정적이므로 계산은 즉시 끝내고, 저장된 실행 결과를 화면에서 시간에 맞춰 재생한다. 현장에서 실시간으로 보였던 결과는 '수신 순서 재생' 모드로 따로 재현한다.
5. **반복 평균만으로는 정확도가 보장되지 않는다.**
   - 중앙값은 회차마다 독립적인 오차만 줄인다(√N).
   - 같은 장소에서 매번 같은 쪽으로 틀리는 GPS 편향(건물 반사)은 그대로 남는다.
   - 그래서 신뢰 폭은 재현성만 보여준다. 정확도는 위치를 아는 앵커 지점에서 따로 재야 하므로, 검증(9)에 앵커 검문점 오차를 처음부터 넣는다.

## 2. 용어와 데이터 계층

'Run'이 두 가지 뜻으로 쓰이므로 구분한다.

| 용어 | 뜻 | 저장 |
|---|---|---|
| 실행(fusion run) | 한 세션을 한 알고리즘 버전·변형으로 한 번 처리한 결과 | `fusion_runs`(기존) + 스냅샷 테이블(신규) |
| 회차(pass) | 경로를 한 번 지나간 구간 = (실행, 시작 시각, 끝 시각, 방향). 원 목록의 'Raw Run' | `route_passes` |
| 경로(route) | 같은 길로 취급할 회차 묶음과 그 정의(시작 A, 끝 B) | `routes` |
| 대표 경로 / 대표점 | 경로의 회차들로 만든 선과 1 m 간격의 점 | `canonical_paths`, `canonical_points` |
| 신뢰 폭(corridor) | 대표점별 회차 간 횡방향 퍼짐으로 만든 띠 | 대표점의 σ로 계산 |
| 앵커 | 위치(필요하면 높이)를 아는 지점. 출입구 문턱, 계단 첫 단, 교차로 | `anchors`(묶음 2) |

각 계층은 바로 아래 계층만 읽는다. 위 계층을 다시 만들어도 아래 계층은 지우지 않는다.

```
L0 원본 센서·마커 (불변)
L1 원본 품질 판정 qc-v1                        ← 7
L2 실행 스냅샷 (전방·최종 궤적, GPS 판정, 사건)  ← 1, 8
L3 궤적: 캠퍼스 좌표 + 1 m 재표본               ← 2, 3
L4 경로·회차, 방향·유사도                       ← 4
L5 대표 경로·신뢰 폭·검증                       ← 5, 6, 9
L6 이동 공간·앵커                               ← 11–14
L7 내보내기                                     ← 18
```

## 4. 묶음 1 상세

### 4.1 캠퍼스 공통 좌표계 (2)

- `backend/src/geo/campus-frame.ts`에 좌표계 하나를 정의한다. 식별자는 `skuniv-5186-v1`이다.
  - x = EPSG:5186 동향 − 201,100 m, y = 북향 − 557,250 m. 캠퍼스 경계 중심(201,116 / 557,268)을 50 m 단위로 반올림한 값이다.
  - z = 정표고(인천 평균해수면) = 타원체고 − N(KNGeoid18 23.377 m). DEM과 VWorld 지도 높이와 같은 기준이다.
  - 캠퍼스 범위는 x −130~+166 m, y −150~+174 m 정도다.
- EPSG:5186을 쓰는 이유:
  - 캠퍼스 지도 SHP, DEM 격자, 건물 도형, 앞으로 받을 QGIS 자료가 모두 이 좌표계라 재투영이 필요 없다.
  - 캠퍼스(동경 127.012°)에서 축척 오차는 2×10⁻⁸ 미만이고, 도북과 진북의 차이(자오선 수렴각)는 0.008°다. 사실상 동·북·상(ENU) 미터 좌표로 쓸 수 있다.
- `tm.ts`에 역변환(`tmInverse`)을 추가한다. PostGIS 기준값과 1 cm 이내, 왕복 1 mm 이내를 테스트한다.
- 기존 엔진은 바꾸지 않는다. 실행 스냅샷을 저장할 때 엔진이 낸 위경도를 캠퍼스 좌표로 정확히 변환해 함께 저장한다. v4 내부 접평면 좌표의 근사 오차는 캠퍼스 범위에서 cm 수준이다. 새 엔진(v5 이후)은 처음부터 이 좌표계를 쓸 수 있다.
- 높이 영점이 없는(NONE) 회차의 z는 기압 상대값이다. 표시를 붙이고, 세션 간 높이 비교에서는 따로 다룬다(4.8).
- `spatial.ts`의 위경도 근사 거리 계산을 이 좌표계로 바꾸면 v3/v3.1 결과가 달라진다. 별도 revision 작업으로 미룬다.

### 4.2 실행 스냅샷과 변형 실행 (8의 저장 부분)

지금은 `replaceOutputs`가 같은 버전의 이전 결과를 지운 뒤 새 결과를 넣는다. v4 코드를 고쳐 재처리하면 수정 전 궤적을 다시 볼 수 없고, `fusion_runs`의 지표만 남는다.

- 재처리 한 번을 변하지 않는 스냅샷으로 저장한다. 식별자는 기존 `fusion_runs.id`다.
  - `fusion_runs`에 추가하는 컬럼:

    | 컬럼 | 내용 |
    |---|---|
    | `revision` | 엔진 revision |
    | `variant` | 변형 이름. 없으면 기본 |
    | `overrides` | 바꾼 파라미터 |
    | `mode` | SENSOR_TIME 또는 AS_RECEIVED |
    | `code_ref` | git HEAD와 작업 트리 변경 여부 |
    | `published` | `fused_positions`에 게시했는지 |
    | `pinned` | 정리에서 제외할지 |

  - `fusion_run_positions`: 실행별 궤적. `stage` FORWARD(실시간과 같은 전방 결과)와 FINAL(스무딩 결과)을 둘 다 저장한다. 캠퍼스 좌표 x·y·z, σ, 높이 영점 출처, 출처(source), 방향, 건물을 함께 둔다. finalize가 없는 버전은 FINAL만 둔다.
  - `fusion_run_fixes`: 원본 GPS 한 점마다 엔진이 내린 판정이다. 전방 채택 여부와 사유, 혁신 거리, 스무더 가중치와 잔차를 둔다.
  - `fusion_run_events`: 걸음, 계단, 방향 구간, 재앵커, 지면 접촉, 영점 같은 엔진 사건이다. 지금 v3.1 전용인 `fusion_sensor_events`를 실행 단위로 일반화한 것이다.
- `fused_positions`는 버전별로 '게시된' 결과로 그대로 둔다. 실시간 처리, 기존 Preview, 마커 스냅이 계속 이 테이블을 읽는다. 지금의 재처리는 '스냅샷 저장 + 게시'가 된다.
- 변형 실행: `FusionAlgorithm.withConfig(overrides)`로 설정 일부를 바꾼 인스턴스를 만든다. 바뀐 설정은 config hash에 자동으로 들어간다. 변형 실행은 기본적으로 게시하지 않는다.
- 보관: 고정(pinned)한 실행과 (세션, 버전, 변형)별 최근 5개를 남기고 `fusion:prune`으로 정리한다. 대표 경로가 참조하는 실행은 자동으로 고정한다. 전 세션의 v4 출력이 약 1만 5천 점이라 용량 부담은 없다.
- 엔진 코드를 고치고 revision을 올리지 않았더라도 `code_ref`로 어느 코드의 결과인지 구분할 수 있다.

### 4.3 Recorded Session Replay (1)

- 실시간 처리(`applyLive`)와 재처리(`replaySession`)의 공통 부분을 `fusion.pipeline.ts`로 뽑는다. 재정렬 버퍼, 공간·지형 주석, `algo.process`/`flush`/`finalize` 호출이 여기에 들어간다.
  - 실시간 = 파이프라인 + DB·소켓 출력
  - Replay = 파이프라인 + 스냅샷 출력
  - 보정 로직은 한 곳에만 있다.
- 재생 모드:
  - **SENSOR_TIME** (기본, 지금 재처리와 같음): 원본 전체를 센서 시각순으로 넣고 flush·finalize까지 한다. 이것이 정식 결과다.
  - **AS_RECEIVED**: 서버가 실제로 받은 순서대로 배치를 다시 만들어 실시간 경로(재정렬 창 3.5초 포함)에 넣는다. 배치는 샘플의 `created_at`으로 묶는다(한 배치는 한 트랜잭션 시각을 공유한다). 현장에서 실시간으로 보였던 궤적과, 늦게 도착해 버려진 샘플을 재현한다.
- 재생 속도: 계산은 항상 즉시 끝내고, Lab 화면이 저장된 실행을 시간축으로 재생한다.
  - 1x / 5x / 20x / Instant, 일시정지, 시간 슬라이더를 둔다.
  - 재생 중에는 FORWARD 궤적이 늘어나고 원본 GPS 점이 채택·거부 색으로 나타난다. 방향 구간 시작, 재앵커, 계단 같은 사건도 그 시각에 표시한다.
  - 끝까지 가면 FINAL(스무딩) 궤적과 겹쳐 본다.
  - 엔진이 결정적이므로 천천히 계산한 결과와 즉시 계산한 뒤 천천히 재생한 결과는 같다. 서버 부하나 소켓 상태 관리 없이 몇 번이고 되감을 수 있다.
- API:
  - `POST /api/v1/sessions/:id/replays` `{algorithmVersion, variant?, overrides?, mode, publish}` → `runId`
  - `GET /api/v1/runs/:runId`, `/positions?stage=`, `/fixes`, `/events`
- CLI: `npm run fusion:replay -- --session=<id>|--all --version=fusion-v4 [--set gpsGateChi2=9] [--variant=chi9] [--mode=as-received] [--publish]`. 기존 `fusion:reprocess`는 '게시하는 replay'로 남긴다.
- 리팩터링 검증:
  - 리팩터링 전후로 모든 버전·23개 세션의 출력이 완전히 같아야 한다(출력 해시 비교).
  - `check:delayed-upload`가 통과해야 한다.
  - 순서대로 들어온 세션은 AS_RECEIVED 결과가 실시간 저장 결과와 같아야 한다.

### 4.4 원본 품질 판정 qc-v1 (7)

- `backend/src/modules/qc/`는 엔진과 독립된 순수 함수다. 세션의 원본 GPS를 센서 시각순으로 판정해 `raw_location_qc`에 저장한다. 저장 항목은 세션, 원본 sequence, qc 버전, 상태, 사유 목록, 근거 수치다. 원본은 그대로 둔다.
- 상태는 ACCEPTED / SUSPECT / REJECTED다. 시작 규칙은 아래와 같고, 값은 qc 버전에 묶어 기록한 뒤 현장 데이터로 조정한다.

| 사유 | 조건 | 상태 |
|---|---|---|
| INVALID | 정확도 ≤ 0 또는 없음, 좌표 비정상 | REJECTED |
| PRE_SESSION | 세션 시작 30초 전보다 이전(iOS 캐시 위치) | REJECTED |
| DUPLICATE | 같은 시각 중복 | REJECTED |
| LOW_ACCURACY | 수평 정확도 > 50 m (v4 기준과 같음) | REJECTED |
| WEAK_ACCURACY | 20~50 m | SUSPECT |
| OUTSIDE_CAMPUS | 캠퍼스 밖이고 경계까지 거리 > 정확도 | REJECTED (지도 작성에서 제외) |
| JUMP | 직전 채택 점 대비 거리 > 3 m/s × Δt + 2√(acc₁² + acc₂²) + 5 m | REJECTED |
| SPIKE | 앞뒤 점은 서로 가까운데(2σ 이내) 이 점만 3σ 넘게 벗어남 | REJECTED |
| VEHICLE | 속도 ≥ 3 m/s가 10초 이상 이어지고 걸음이 없음 | SUSPECT (보행 지도에서 제외) |

- 융합 결과 점도 같은 방식으로 판정한다. 수평 σ > 15 m, 캠퍼스 밖, (묶음 3 이후) 통행 불가 영역에 해당하면 회차 재표본에서 빼고 사유를 남긴다.
- qc-v1은 v4의 동작을 바꾸지 않는다(v4에는 자체 게이트가 있다). 이 판정을 엔진 입력으로 쓰려면 새 버전으로 추가한다.
- 화면에서는 원본 점을 판정 색으로 칠하고, 클릭하면 사유를 보여준다.
- API `GET /sessions/:id/qc`, CLI `npm run qc:run -- --all`. 세션 finalize 때 자동 계산한다.

  - 직선 150 m
  - ㄱ자 경로
  - A→B→A 왕복
  - 같은 경로 5회(회차별 독립 잡음 + 장소 편향 공유)
  - 이상치 묶음이 낀 회차
  - 30 m 옆의 다른 길

### 4.6 궤적 재표본 (3)

`backend/src/modules/trajectory/resample.ts`는 결정적인 순수 함수다.

1. 실행의 FINAL 궤적을 캠퍼스 좌표로 읽고, 판정에서 빠진 점을 제외한다.
2. 시간 공백 > 10초, 순간 이동 > 15 m인 곳에서 조각을 나눈다. 조각 사이는 보간하지 않는다.
3. 누적 이동거리 s를 계산하고, s = 0, 1, 2 … m마다 x·y·z·t·σ를 선형 보간한다. 간격은 기본 1 m, 선택 0.5 m다.
4. 정지 구간은 s가 늘지 않아 자연히 한 점으로 모인다. 머문 시간은 점의 속성으로 남긴다.

- 원본과 실행 스냅샷은 그대로 두고 재표본 궤적을 따로 만든다. API `GET /runs/:id/resampled?ds=1`로 제공한다.
- 대표 경로를 만들 때 쓰인 회차 재표본은 재현성을 위해 결과와 함께 저장한다.
- 완료 확인: 같은 정답 경로를 0.8 m/s와 1.5 m/s로 걸은 합성 회차가 1 m 간격 점열로 바뀐다. 점 수가 경로 길이/간격과 맞고, 두 회차가 서로 잡음 수준 안에 있다.

### 4.7 회차 추출, 방향·유사도 판정 (4)

- 경로 정의: 이름, 시작 지점 A, 끝 지점 B(지도 클릭 또는 마커 선택), 허용 폭 W(기본 20 m).
- 회차 추출:
  - 자동: 궤적이 A 반경(기본 max(15 m, 2σ)) → B 반경 순으로 지나가면 A→B 회차, 반대 순서면 B→A 회차로 자른다. 한 세션에 왕복이 여러 번 있어도 회차가 각각 잘린다.
  - 수동: 세션과 시간 범위를 직접 지정한다.
- 방향: A·B 통과 순서로 정하고, 기준선에 대한 DTW 거리를 정방향과 역방향으로 각각 계산해 확인한다. 역방향 회차는 점 순서를 뒤집고 s를 A부터 다시 잰다. 원래 방향은 기록해 둔다.
- 유사도 검사(기준선 = 현재 대표 경로, 처음에는 medoid 회차):

| 검사 | 통과 조건(시작값) | 실패 사유 |
|---|---|---|
| 덮는 비율 | 회차 점의 80% 이상이 기준선에서 W 이내 | DIFFERENT_PATH |
| 길이 비 | 기준선의 0.75~1.33배 | LENGTH_MISMATCH |
| 평균 정렬 거리 | DTW 평균 ≤ 10 m | DIFFERENT_PATH |
| 경로 범위 | 경로의 30% 이상을 덮음 | TOO_SHORT |

- 경로 일부만 지난 회차는 PARTIAL로 두고, 덮는 구간의 대표점에만 기여시킨다. 거부된 회차도 사유와 함께 목록에 남긴다.
- 완료 확인:
  - 합성 A→B 3회 + B→A 3회로 만든 대표 경로가 A→B 6회 결과와 잡음 수준 안에서 같다.
  - 30 m 옆 다른 길은 DIFFERENT_PATH로 거부된다.

### 4.8 대표 경로 생성 pathfusion-v1 (5)

대표 경로 알고리즘도 엔진처럼 버전(`pathfusion-v1`)과 파라미터 해시를 기록한다.

1. 입력: 채택된 회차의 1 m 재표본(정방향으로 맞춤). 품질 가중치는 묶음 4 전까지 모두 1이다.
2. 초기 기준선: medoid 회차(다른 회차들과의 DTW 거리 합이 가장 작은 회차).
3. 반복(최대 5회, 변화 < 0.1 m면 멈춤):
   1. 각 회차를 기준선에 DTW로 정렬한다. 띠 폭은 길이의 15%이고 단조 증가 대응만 허용한다.
   2. 기준점마다 회차별 대응 점들의 평균을 구한다. 천천히 걸은 회차도 한 표만 갖는다.
   3. 기준점에서 회차별로 법선 방향 횡오프셋 l과 높이 z를 구한다.
   4. 새 위치 = 기준점 + median(l) × 법선, 새 높이 = median(z).
   5. 중앙값에서 max(3σ̂, 3 m) 넘게 벗어난 표는 이상치로 표시하고 뺀다. 한 회차가 30% 넘는 지점에서 빠지면 그 회차 전체를 RUN_OUTLIER로 제외하고 다시 계산한다.
   6. 결과 선을 5 m 이동 중앙값으로 살짝 다듬고 1 m로 다시 재표본해 다음 기준선으로 쓴다.
4. 대표점은 `CanonicalPoint { s, x, y, z, sampleCount, sigmaXY, sigmaZ, seXY, confidence, contributors }`다.
   - `sigmaXY` = 1.4826 × MAD(l): 회차 간 횡방향 퍼짐. `sigmaZ`도 같은 방식이다.
   - `seXY` = 1.2533 × sigmaXY / √n: 대표점 자체의 표준오차.
   - `confidence` = (1 − e^(−n/3)) × e^(−sigmaXY / 5 m): 0~1 경험 점수이며 확률이 아니다.
   - n < 3인 구간은 LOW_SAMPLES로 표시한다.

- 산술 평균 대신 법선 방향 중앙값을 쓰는 이유는 회차의 절반 가까이가 튀어도 대표점이 끌려가지 않기 때문이다. 합성 시험: 깨끗한 5회에 20 m 벗어난 회차 2개를 더해도 대표 경로 변화가 1 m 미만이어야 한다(두 회차는 RUN_OUTLIER로 제외).
- 높이:
  - 영점이 TERRAIN이나 GPS인 회차로 대표 높이를 정한다.
  - 영점이 NONE인 회차는 대표 높이와의 중앙값 차이만큼 맞춘 뒤 퍼짐 계산에 넣는다.
  - 그 차이는 '세션 간 Z 영점 불일치'로 따로 보고한다.
- 저장:
  - `routes`
  - `route_passes`: 실행, 시간 범위, 방향, 유사도 지표, 상태와 사유
  - `canonical_paths`: 알고리즘, 파라미터, 입력 회차와 그 실행, 좌표계 ID, 지표
  - `canonical_points`
- API `POST /api/v1/routes/:id/canonical`, CLI `npm run routes:build -- --route=<id>`.

### 4.9 신뢰 폭 (6)

- 대표점별 반폭 w = max(2 × sigmaXY, 0.5 m). 횡방향 퍼짐이 정규분포면 회차의 약 95%가 띠 안에 든다.
- 좌우 오프셋 선으로 띠 다각형을 만들고, 신뢰 등급별 구간으로 나눠 색을 칠한다.
  - 초록: σ < 2 m이고 n ≥ 5
  - 노랑: σ < 5 m
  - 빨강: σ ≥ 5 m 또는 n < 3
- 지도 레이어는 각각 켜고 끌 수 있다: 회차 궤적(Raw Runs), 대표 경로, 신뢰 폭, 원본 GPS(판정 색).
- 대표 경로나 띠를 클릭하면 s, n, σXY, σZ, seXY, 신뢰도, 기여 회차(세션·시각·방향), 제외된 회차와 사유를 보여준다.
- 완료 확인:
  - 절반은 개활지(σ 3 m), 절반은 건물 사이(σ 12 m)인 합성 경로에서 두 구간의 색이 갈린다.
  - 실데이터로는 9절의 R1(개활지)과 R2(건물 사이)를 비교한다.

### 4.10 검증과 bench (9)

- 분할 방식: 회차 하나씩 빼기(기본), k-fold(회차 10개 이상), 직접 지정.
- 시험 회차마다 나머지 회차만으로, 같은 알고리즘·파라미터로 대표 경로를 만든다. 그다음 시험 회차의 각 점에 대해 다음을 계산한다.
  - XY 오차: 대표 경로 폴리라인까지의 최근접 거리(캠퍼스 좌표)
  - Z 오차: 가장 가까운 대표점과의 높이 차(4.8의 영점 규칙 적용)
  - 띠 안에 있는지 여부
- 지표:
  - Median / P95 / Max XY 오차, Median / P95 Z 오차
  - 띠 포함률: 약 95%가 나와야 신뢰 폭이 제대로 맞춰진 것이다
  - Rejected Point Ratio: 회차 시간대 원본 GPS 중 qc REJECTED 비율. 엔진이 가중치를 낮춘 비율은 따로 보고한다
  - 앵커 검문점 오차: 앵커에서 찍은 마커 시각의 융합 위치와 앵커 위치의 차이. 앵커 목록이 생기기 전에는 같은 지점에서 찍은 마커끼리의 퍼짐으로 대신한다
- 결과는 `validation_reports`에 저장한다. 저장 항목은 경로, 대표 경로 알고리즘·파라미터, 입력 실행의 버전·변형, 분할, 회차별 지표다.
- 화면에서는 시험 회차를 오차 색으로 칠하고, 각 점에서 대표 경로까지 최근접 선을 그린다.
- bench (핵심 개발 순환):

```bash
npm run bench -- --suite=default --candidate=fusion-v4 --set gpsGateChi2=9 --baseline=latest
```

  1. 묶음(`backend/bench/suites/default.json`: 경로와 원천 세션 목록)의 세션을 후보 설정으로 replay해, 게시하지 않는 스냅샷으로 저장한다.
  2. 회차를 추출하고 대표 경로를 만든 뒤, 회차 하나씩 빼기 검증을 하고 앵커 오차를 잰다.
  3. 기준선과 후보의 지표를 나란히 출력하고 차이를 보인다. 결과는 저장해 화면에서도 본다.
- 해석 주의:
  - 회차들이 같은 장소의 편향을 공유하므로, 회차 빼기 오차는 실제 오차보다 작게 나온다.
  - '정확도 개선'은 앵커 오차가 나빠지지 않았을 때만 주장한다.
- 로그와 CLI 출력에는 집계 지표만 내고 좌표 목록은 출력하지 않는다(개인 위치 데이터 로그 금지 원칙).

  - 1 m 격자 밀도(통과 회차 수)
  - 대표 표시용 medoid 궤적(평균이 아님)
- 완료 확인: 합성 광장 4방향 횡단이 4개 이동 패턴으로 남고, 하나의 평균선으로 합쳐지지 않는다. 실데이터는 9절의 광장 측정으로 확인한다.

### 지도 제약 (13)

- `mapPrior(track, spaces, cfg)`가 스무더에 넣을 약한 의사 관측을 만든다. v4 rev 3 실내 계단 앵커와 같은 방식이다.
  - CORRIDOR: 중심선 쪽 횡방향 의사 관측, σ = max(폭/2, 1 m). 강제로 붙이지 않는다.
  - OPEN_AREA: 안에서는 당기지 않는다. 경계 밖으로 2 m 넘게 나가면 경계 쪽 의사 관측(σ 2 m)을 넣는다.
  - NO_GO, 포털을 거치지 않고 들어간 건물 안: 그곳의 GPS는 σ × 3으로 약하게 쓰고, 위치는 낮은 신뢰도로 표시한다.
- 공간 유형별 강도는 설정값이고 config hash에 들어간다. v4 + 지도 제약을 새 버전(v5 후보)으로 등록하고 bench로 v4와 비교한다.
- 주의: 대표 경로에서 만든 corridor를 제약으로 쓰면, 시험 회차가 그 corridor 생성에 들어가지 않아야 한다. bench는 학습 회차로만 제약을 만들거나, QGIS에서 그린 도형만 쓴다.

### 내보내기·가져오기 (18)

- 내부 표준 JSON `campus-mobility-map/1`에 담는 내용:
  - 좌표계 정의: EPSG:5186, 원점, KNGeoid18 N, 높이 기준
  - 지도 버전
  - 대표 경로와 대표점
  - corridor, 광장, 포털, 앵커
  - 출처: 입력 실행, 알고리즘 버전, 파라미터, 생성 시각

| 측정 | 방법 | 목적 |

| R2 건물 사이 약 100 m | 정방향 5회 + 역방향 5회 | 다중경로 구간과 비교 |
