# 보행·관성·기압 센서 중심 퓨전 리팩토링 계획

작성일: 2026-10-02  
상태: `fusion-v3.1` 구현 및 기존 세션 19개 재처리 완료. 실시간 기본 버전은 현장 비교 전까지 v2.1 유지.

## 1. 목표와 범위

일상적인 이동량은 보행 센서, 방향 변화는 기기 자세, 상대 높이는 기압계로 계산한다. GPS(Core Location 위치 관측)는 검증된 초기 앵커와 간헐적인 위치 재보정에만 사용한다. 센서 전체에 고정 비율을 배분하지 않고, 각 센서가 맡는 상태와 갱신 권한을 분리한다.

기존 v3와 비교할 수 있도록 새 구현은 `fusion-v3.1`로 등록한다. v2.1 엔진을 호출하는 래퍼 대신 독립 상태와 처리 흐름을 사용하고, 좌표 변환·타임라인·공간 판정 등 공통 도구는 재사용한다. 실시간 기본값은 검증 전까지 v2.1을 유지한다.

이번 범위는 서버 엔진, 기존 센서 입력 연결, 상태 저장·표시, 검증과 과거 세션 비교다. 고정 기준점 관리, QR 스캔, 수동 앵커 입력 화면은 후속 작업이다. 엔진의 앵커 인터페이스는 이 기능을 수용할 수 있도록 분리한다.

## 2. 현재 코드에서 확인한 문제

- `fusion-v3.engine.ts`는 GPS 신뢰도를 검사한 뒤 `processObservationV21`을 호출한다. 최초 연속 관측을 통과하면 후속 GPS도 반복해서 내부 엔진에 전달한다.
- v2.1은 전달된 GPS로 매번 XY를 보정하고, GPS 경로·군집으로 재앵커하며, course/두 지점으로 방향을 갱신하고, GPS 높이로 높이 기준도 보정한다. 현재 v3는 GPS 사용 조건이 엄격하지만 센서 중심의 독립 엔진은 아니다.
- `applyPedometer`는 `distance`가 없으면 반환한다. 타임라인에 걸음 수가 있어도 거리 대체 추정에 사용하지 않는다.
- motion 원본에는 회전 속도·중력·roll/pitch/yaw가 저장되지만, fusion 로더는 yaw와 사용자 가속도만 가져온다. 원본에 존재한다는 사실과 실제 데이터가 유효하게 채워져 있다는 사실은 구분해야 한다.
- 위치나 방향을 확보하지 못하면 보행 이동을 적용하지 못한다. 위치 출력만으로는 왜 추적이 대기 중인지 충분히 표현하기 어렵다.
- 직전 재처리에서 19개 세션의 위치 관측 632건 모두 앵커로 사용되지 않았다. 캠퍼스 내부에서 정확도 조건을 통과한 1건도 연속 관측 조건이 부족했다. 이번 변경만으로 기존 세션에 절대 위치가 생긴다고 보장하지 않는다.

## 3. 센서별 역할

| 자료 | 주된 역할 | 적용 원칙 |
| --- | --- | --- |
| 보행 거리 | 수평 이동량 | 유효한 누적 거리의 차이를 우선 사용 |
| 걸음 수 | 거리 누락 시 대체 | 걸음 수 증가 × 설정된 보폭. 대체 사용과 더 큰 불확실도를 기록 |
| 기기 자세 yaw | 상대 방향 변화 | 초기 절대 방향에 변화량을 적용. 기기 회전과 보행 방향의 관계가 유지되는 구간에서 사용 |
| 사용자 가속도 | 정지·이동 판정 | 최근 보행 증거와 함께 판단. 거리 계산을 위한 가속도 이중 적분은 도입하지 않음 |
| 회전 속도·roll/pitch·중력 | 자세 연속성·급격한 취급 변화 검사 | 유효한 기존 필드가 있는 경우 보조 신호로 사용. 동일한 회전을 yaw와 중복 적분하지 않음 |
| 상대 고도 | 수직 이동량 | 기압계의 상대 고도 변화가 주도. 수평 정지 중에도 갱신 |
| GPS 위치 | 초기 위치·간헐적 재앵커 | 자격을 갖춘 관측 묶음만 독립 앵커 이벤트로 전환 |

보폭은 설정·해시에 포함되는 실험값으로 시작하고 알려진 거리에서 보정한다. 센서 누락 때문에 GPS 연속 보정으로 자동 전환하지 않는다. 자기장·절대 방위나 자세 기준 좌표계처럼 현재 계약으로 확인되지 않은 정보가 존재한다고 가정하지 않는다.

## 4. 새 처리 흐름

```text
원본 저장 → 측정 시각 정렬 → 센서별 품질·연속성 검사
                              ├─ 보행 거리/걸음 → 수평 이동 예측
                              ├─ 자세/가속도 → 방향·정지 상태 갱신
                              ├─ 기압 → 상대 높이 갱신
                              └─ GPS → 앵커 후보 검증 → 자격 있는 앵커 이벤트
                                                  ↓
                        예측 상태 + 필요한 시점의 앵커 보정
                                                  ↓
                     불확실도·캠퍼스 검사 → 위치 또는 추적 상태 발행
```

### 보행 거리와 정지 판정

- 기본 거리 증분은 보행 센서 누적 거리의 차이다. 유효한 거리 증분을 얻을 수 없는 구간만 걸음 수 차이로 대체한다.
- 거리·걸음 누적 기준을 따로 관리한다. 대체 추정 뒤 누적 거리가 복귀했을 때 이미 반영한 이동량을 다시 더하지 않는다. 공통 시각의 기준을 확보할 수 없으면 복귀 샘플을 기준점으로 삼고 불확실도를 올린다.
- 음수·비정상 급증·중복 시각·서비스 재시작·지연 업로드를 구분한다. 긴 공백의 총거리를 마지막 방향 하나로 적용하지 않는다.
- 정지는 가속도만으로 확정하지 않는다. 최근의 유효한 걸음 증가와 거리 증분을 함께 보고 진입·해제 조건을 분리한다. 자료가 오래되었거나 부족하면 `UNKNOWN`으로 다룬다.
- 정지 시 수평 위치를 유지한다. 엘리베이터처럼 걸음 없이 높이가 바뀌는 상황에 기압 갱신까지 정지시키지 않는다.

### 방향

- 위치 앵커와 방향 앵커는 별도다. 위치 하나만으로 방향을 만들지 않는다.
- 이번 GPS 시작 경로에서는 자격 있는 앵커 관측 중 충분한 실제 보행과 오차 대비 충분한 변위가 있을 때만 초기 방향을 구한다. GPS course를 매 관측마다 혼합하는 동작은 제거한다.
- 방향 확보 뒤에는 yaw 변화로 방향을 진행한다. GPS 재앵커가 위치를 보정하더라도 방향은 별도 자격을 통과해야 변경한다.
- 초기 구현의 현장 검증 조건은 휴대폰과 보행 방향의 관계가 일정한 휴대 자세다. 휴대폰을 손에서 돌리는 동작을 보행 회전으로 완벽히 구분할 수 있다고 가정하지 않는다.
- 센서 구간 변경·긴 공백·자세의 큰 변화에서 방향 신뢰도를 낮추고 필요한 경우 재확보한다. 방향이 없거나 사용할 수 없으면 걸음 거리만 기록하고 지도상 이동을 보류한다. 이후 방향이 생겨도 과거 걸음을 한꺼번에 적용하지 않는다.
- 고정 시작점 후속 기능에서는 시작 방향이나 기준 방향 보정 절차까지 함께 연결한다.

### 높이

- 초기 기준 시점의 상대 고도를 0으로 두고 이후 기압 변화로 상대 Z를 계산한다. 절대 높이 미확보 시 `ellipsoidalAltitude`는 null로 유지한다.
- 이번 버전에서는 GPS 고도의 반복 보정을 제거하고 상대 높이 추적을 우선한다. 알려진 절대 높이와 높이 기준 체계가 제공되는 후속 앵커 기능에서 절대 높이를 연결한다.
- 센서 재시작 시 현재 상대 높이를 유지하고 새 기준값을 설정한다. 공백 중 이동량은 알 수 없으므로 수직 불확실도에 반영한다. 급격한 센서 이상치를 분리한다.
- 층수나 실내외를 건물 평면 도형으로 확정하지 않는다. 지도 XY가 대기 중이어도 상대 높이와 품질 상태는 진단 자료로 제공한다.

## 5. GPS는 앵커 이벤트로만 사용

- 최초 앵커의 기존 조건(정확도 5m 이하, 5개 이상, 3초 이상, 인접 간격 2초 이하, 캠퍼스 내부)은 비교를 위한 출발값으로 유지한다. 결과를 만들기 위해 자동 완화하지 않는다.
- 연속 관측 통과 여부와 실제 앵커 적용 여부를 구분한다. 후속 관측 하나마다 위치를 보정하지 않고, 매 앵커마다 새로운 검증 묶음을 요구한다. 동일 관측 묶음을 중복 사용하지 않는다.
- 움직이는 동안의 관측을 단순 평균해 과거 위치로 당기지 않는다. 앵커 적용 좌표와 시각은 마지막 자격 관측에 맞추고 이전 관측은 검증 근거로 사용한다.
- 추적 중 재앵커는 불확실도·관측과 예측의 차이·센서 이동 증거·보정 후 캠퍼스 판정을 함께 검사한다. 지나치게 큰 충돌은 강제 순간 이동 대신 재획득 상태로 전환한다.
- 일반 재앵커의 최소 간격은 30초를 실험 시작값으로 둔다. 최초 초기화·재획득은 이 간격 제한의 예외다. 보정량 상한과 위치 오차 추정에 따른 보정 강도는 설정으로 분리하고 기록한다.
- 정지 중에는 GPS 흔들림이 보행처럼 누적되지 않게 한다. 보정이 필요해도 앵커 이벤트로 명시하고 보행 거리와 분리한다.
- 부적격 GPS는 XY·방향·높이·보폭·정지 판정에 영향을 주지 않는다. Wi-Fi 상태는 가중치 조건으로 쓰지 않는다.

## 6. 초기 앵커 부재·신뢰도 저하·공간 정책

위치 상태(`UNANCHORED`, `TRACKING`, `REACQUIRE_REQUIRED`), 방향 상태(`UNKNOWN`, `VALID`, `DEGRADED`), 센서 품질을 별도 관리한다. 화면에는 이를 조합해 ‘시작 위치 대기’, ‘방향 대기’, ‘센서 추적 중’, ‘재보정 필요’를 표시한다.

- 앵커가 없으면 걸음·상대 높이·센서 상태는 처리하되 위경도 위치를 만들지 않는다. 이번 변경에서도 기존 19개 세션의 지도 궤적은 0건일 수 있다.
- 보행 거리·방향 불확실도·센서 공백·마지막 앵커 이후 경과에 따라 위치 불확실도를 갱신한다. 센서 중심으로 바뀌었다는 이유만으로 신뢰도를 올리거나 허용 한도를 늘리지 않는다.
- 기존 수평 불확실도 20m 상한은 초기 비교에 유지한다. 이를 넘거나 예측이 캠퍼스 밖으로 나가면 유효 위치 발행을 중단하고 재획득한다. 센서 누적 기준은 계속 관리해 재개 시 이동량이 몰려 적용되지 않게 한다.
- 경계 불확실 구간은 유효 위치로 발행하지 않는다. 중단·재개 구간은 별도 구간 ID로 표시한다.
- 마지막 유효 위치의 측정 시각을 유지한다. 상태 갱신 시각과 위치 측정 시각을 분리한다.
- 건물은 위치 결과에 참고 태그만 붙인다. 건물이 없는 지하주차장에서도 같은 추정 정책을 적용한다.

## 7. 코드·저장·화면 변경

1. **독립 엔진:** `fusion-v31.engine.ts`, `fusion-state-v31.ts`와 보행·방향·기압·앵커 정책 모듈을 추가한다. GPS 입력을 무효 좌표로 바꿔 구 엔진에 주입하는 방식은 사용하지 않는다.
2. **관측 연결:** `fusion.timeline.ts`, `fusion.repository.ts`, 실시간 DTO 변환에 동일한 필드를 연결한다. 저장된 회전 속도·중력·자세 정보를 활용하되 null과 구버전 데이터도 처리한다. 구현 전 세션별 유효 필드 비율·주기·공백을 집계한다.
3. **등록·재현성:** `fusion.algorithms.ts`, 설정, service, 재처리 CLI를 수정한다. 현재 service의 `version === 'fusion-v3'` 지도 검사·설정 해시 분기를 공간 지도가 필요한 알고리즘의 명시적 속성으로 바꿔 v3.1에도 적용한다. revision·지도·보폭·정책 설정을 재현 정보에 포함한다.
4. **진단 저장:** 새 마이그레이션으로 위치 출력이 없어도 저장되는 상태/앵커 이벤트 이력을 추가한다. 세션·알고리즘·결정적 이벤트 순번으로 구분하고 재처리 시 해당 버전 이력을 트랜잭션으로 교체한다. 후보 GPS sequence, 앵커 출처·측정 시각·보정량·신뢰도·적용/거절 사유를 기록한다.
5. **조회·실시간:** 추적 상태 조회와 실시간 상태 이벤트를 추가한다. 융합 위치에는 이동 거리 출처, 방향 품질, 높이 기준, 마지막 앵커 시각을 제공한다. GPS 판정 기록은 실제 앵커 적용과 후보 대기를 구분한다. 종료 flush와 서버 복구에서도 이벤트를 빠짐없이 저장한다.
6. **비교 화면:** 기존 버전과 v3.1 비교, 무앵커·방향 부재 사유, 상대 높이, 재보정 시점·위치 이동량을 표시한다. 위치가 0건이어도 처리 완료 버전이 조회·선택되도록 완료 실행 이력과 버전 목록을 연결한다.
7. **후속 앵커 인터페이스:** 절대 위치·적용 시각·출처·위치 불확실도와 선택적 방향·높이 기준을 받는 내부 인터페이스를 둔다. 고정점/수동 이벤트의 영속화·권한·QR 화면은 별도 구현 범위로 남긴다.

## 8. 구현 순서와 검증

1. 센서 가용성 진단과 기존 재처리 지표를 확보한다.
2. 독립 상태·타임라인 연결·거리/걸음 전환을 구현한다.
3. 방향·정지·기압 추적과 연속성 처리를 구현한다.
4. GPS 앵커 정책과 캠퍼스/불확실도 제한을 연결한다.
5. 상태 저장·API·미리보기·재처리 비교 기능을 연결한다.
6. 회귀 테스트·타입 검사·빌드 후 과거 세션을 v3.1로 별도 재처리한다.

검증은 다음 행동을 직접 확인한다.

- 같은 초기 위치·방향에서 GPS가 끊겨도 보행 거리와 회전, 상대 높이가 반영된다. 초기 위치가 없으면 절대 좌표를 만들지 않는다.
- 거리 누락 → 걸음 대체 → 거리 복귀, 센서 초기화와 공백에서 거리 중복이나 순간 이동이 없다.
- 부적격 GPS를 추가하거나 갱신 빈도를 바꿔도 동일 시각의 센서 예측 상태가 변하지 않는다. 출력 주기는 GPS 수신 빈도가 아닌 센서 측정 타임라인에 따른다.
- 정지 중 GPS가 흔들려도 XY가 떠다니지 않는다. 수평 정지 중 유효한 기압 변화는 상대 Z에 반영된다.
- 자세 변경·방향 부재·재시작 시 잘못된 방향으로 이동시키지 않고 품질 저하와 적용 보류를 기록한다.
- GPS 앵커 적용 횟수가 개별 GPS 수신 횟수를 따라 증가하지 않는다. 큰 충돌·경계 이탈·불확실도 초과 후 재개 시 구간과 누적 기준이 올바르다.
- 동일 원본·지도·revision·설정이면 시간순 실시간 처리와 최종 재생의 결과가 일치한다. 배치 분할·중복·지연 수신·서버 복구·종료 flush를 확인한다.
- 건물 태그 유무가 좌표와 앵커 자격에 영향을 주지 않으며 기존 버전 결과와 원본은 보존된다.

현장에서는 알려진 시작 위치와 방향으로 정지·직선·직각 회전·왕복·계단·엘리베이터·지하 이동·휴대폰 자세 변경을 반복한다. 검증용 앵커는 테스트 입력임을 명시하고 실제 관측으로 오인하지 않는다. GPS를 정답으로 삼지 않고 확인 가능한 기준점과 경로 길이를 사용한다.

비교 지표는 기준점 위치 오차, 거리 오차, 방향 오차, 상대 높이 오차, GPS 없는 유효 추적 시간/거리, 상태별 대기 시간, 앵커 적용 횟수·보정량, 캠퍼스 밖 유효 출력 수다. 위치 제공률을 높이기 위해 정확도를 희생했는지도 함께 확인한다. 대표 경로에서 개선을 확인한 뒤 실시간 기본 버전 전환을 결정한다.

## 9. 완료 기준과 한계

보행·자세·기압이 일상 추적을 담당하고 GPS는 기록된 앵커 이벤트로만 영향을 주어야 한다. 위치가 없는 이유도 API와 화면에서 확인할 수 있어야 한다. GPS 앵커가 없는 기존 자료는 상태·상대 센서 정보만 생성되는 것이 유효한 결과다.

절대 위치와 초기 방향 확보, 휴대폰과 보행 방향의 관계, 장시간 센서 누적 오차는 별개의 문제다. 이번 리팩토링은 이 한계를 숨기지 않고 상태와 불확실도로 드러낸다. 이후 지상 고정 기준점과 시작 방향을 연결하면 무앵커 출발 문제를 해결하는 다음 단계로 이어진다.
