# Xcode 전달용: Stop 뒤 업로드 큐에 갇히는 항목과 종료 계약 수정

아래 프롬프트 전체를 Xcode의 코딩 에이전트에 전달한다. `docs/IOS_ANDROID_BASELINE_XCODE_PROMPT.md` 4절("Stop과 종료·동기화 완료를 분리")이 예상했던 문제가 실제 세션에서 확인된 것이다. 그 절의 원칙은 그대로 유효하고, 이 문서는 확인된 결함과 고칠 범위를 구체적으로 정한다. 같은 작업을 이미 진행 중이면 중복 상태 머신을 만들지 말고 이 문서의 요구를 그 작업에 합쳐라.

---

Campus Tracker iOS 앱에서 Stop을 누른 뒤 업로드 대기 항목이 남아 줄지 않는 문제를 고쳐라. 서버는 종료된 세션의 업로드를 거부하지 않는다(종료 뒤 도착한 데이터는 저장하고 최종 결과를 다시 계산한다). 원인은 앱의 업로드 큐다. 먼저 아래 관측이 현재 코드에서도 재현되는지 확인하고 고쳐라. 진행 중인 ARKit·위치 품질 작업은 보존한다. 서버 코드는 수정하지 않는다.

## 1. 관측 (2026-10-14 서버 데이터)

C01 iPhone 세션 4개. 서버 API `GET /api/v1/sessions/{id}`와 `GET /api/v1/sessions/{id}/diagnostic-events`로 다시 확인할 수 있다.

| 세션 | 센서 데이터: 폰 보고 마지막 순번 = 서버 저장 | 도착한 `SENSOR_STARTED` / `SENSOR_STOPPED` | 서버의 manifest 판정 |
|---|---|---|---|
| `97b05bd5` | 위치 4=4, 모션 21=21 | 4 / 1 | 미동기화 (기압·보행계 기대 0, 저장 없음) |
| `c441e46e` | 위치 9=9, 모션 1590=1590, 기압 29=29, 보행계 10=10 | 4 / 0 | 동기화 |
| `a9f96a67` | 위치 8=8, 모션 1894=1894, 기압 35=35, 보행계 12=12 | 4 / 1 | 동기화 |
| `38bf2f6a` | 위치 2=2, 모션 255=255, 기압 4=4 | 0 / 0 | 미동기화 (보행계 기대 0, 저장 없음) |

- 센서 데이터는 모든 세션에서 다 올라갔다. Stop 뒤에 남는 대기 항목은 센서 배치가 아니다.
- Stop 때 센서마다 큐에 들어가는 `SENSOR_STOPPED` 진단 이벤트(4~5개) 중 0~1개만 서버에 도착했다.
- `38bf2f6a`는 세션 시작 시의 `SENSOR_STARTED`도 도착하지 않았다.
- 서버 대시보드의 FINISHED는 "종료 요청을 받았다"는 뜻일 뿐, 업로드 창구가 닫혔다는 뜻이 아니다.

## 2. 확인된 결함 A: 종료 요청 뒤 같은 세션의 항목이 영구히 갇힌다

`Services/CollectionCoordinator.swift`의 `TelemetrySyncCoordinator` 기준(2026-10-14 작업 트리, 줄 번호는 바뀌었을 수 있다):

1. `synchronize()`는 세션 시작 → 센서 배치 → 마커 → ARKit → **종료 요청 → 진단 이벤트** 순서로 한 항목씩 보낸다. 진단 이벤트가 종료 요청보다 뒤다.
2. `stopSession()`은 센서별 `SENSOR_STOPPED`를 큐에 넣은 다음 `telemetrySync.finish(...)`로 종료 요청을 큐에 넣는다. 첫 `SENSOR_STOPPED`는 종료 요청이 큐에 들어가기 전에 이미 전송이 시작되고, 나머지는 종료 요청 뒤로 밀린다.
3. `sendNextFinish`의 ACK 처리가 그 세션의 `sessionStarts`, `serverSessionIds`, `sessionOwners`를 지운다.
4. 전송 대상은 `sessionOwners`가 현재 소유자와 같은 세션의 항목뿐이다(`eligible`). 소유 정보가 지워진 세션의 남은 항목은 다시는 전송되지 않는다. 그런데 `PersistentUploadQueue.pendingCount`는 세션과 무관하게 세므로 화면의 대기 수에는 계속 남는다.

관측과 맞는다: `SENSOR_STOPPED`가 0~1개만 도착했다.

요구:

- **세션별 종료 장벽.** 한 세션의 종료 요청은 그 세션에서 종료 요청보다 먼저 큐에 들어간 모든 항목(센서 배치, 마커, ARKit pose, 진단 이벤트)이 ACK되거나 격리된 뒤에만 보낸다. 큐 전체의 종류별 우선순위만으로 정하지 말고 세션 단위로 판단한다. 다른 세션의 항목 때문에 이 세션의 종료가 막히지 않게 한다.
- **종료 ACK 뒤에도 그 세션의 남은 항목을 보낼 수 있어야 한다.** 소유 정보와 서버 세션 ID는 그 세션의 큐가 완전히 빌 때까지(격리 항목은 보존한 채) 지우지 않는다. 종료 요청 뒤에 생긴 항목(예: 업로드 오류 진단)도 같은 세션으로 보낼 수 있어야 한다.
- **정리 시점.** 그 세션의 큐가 비고 종료 ACK와 아래 4절의 `session:syncComplete` ACK까지 받은 뒤에 세션 상태를 정리한다. 격리된 항목이 남아 있으면 정리하지 않고 "격리 N개"로 표시한다.
- **대기 수 표시.** 전송 가능한 항목, 소유자가 달라 보류 중인 항목, 격리된 항목을 구분해 센다. 어떤 세션에도 전송될 수 없는 항목이 생기면 그 사실을 진단 로그로 남긴다(조용히 쌓이지 않게).
- `logDiagnostic`은 활성 세션이 없으면 아무것도 기록하지 않는다. Stop 이후의 업로드 단계에서 일어난 일(종료 ACK, 격리, 재시도)을 그 세션의 진단으로 남길 수 있게 세션 ID를 받는 경로를 둔다.

## 3. 확인된 결함 B: 샘플이 없는 스트림의 `lastSequences`가 0

`stopSession()`은 `locationSequence` 등을 그대로 `lastSequences`로 보낸다. 순번은 1부터 매기므로(`+= 1` 후 사용) 샘플이 하나도 없는 스트림은 0이 된다. 서버 계약은 "없음"을 `-1`로 정한다(Android 앱은 `-1`을 보낸다). 그래서 서버가 `97b05bd5`, `38bf2f6a`를 "미동기화"로 표시했다. 실제로 빠진 데이터는 없다.

요구: 샘플이 없는 스트림은 `-1`을 보낸다. 샘플이 있으면 마지막으로 큐에 넣은 샘플의 순번이다. 재개(`resumeInterruptedCollection`)로 순번을 건너뛴 경우에도 "실제로 기록한 마지막 순번"이어야 한다. 이 값은 종료 요청을 큐에 넣는 순간 고정해 저장한다.

## 4. 확인된 결함 C: "중단된 수집 종료"가 서버에 알려지지 않는다

`finishInterruptedCollection()`은 로컬 기록만 닫고 서버에 종료 요청을 보내지 않는다. 서버 세션은 ACTIVE로 남는다(2026-10-13 C04 세션이 이 상태로 남아 프리뷰에서 수동 인터럽트를 해야 했다).

요구:
- 이 경로도 종료 요청을 큐에 넣는다: `interrupted: true`, `endedAt` = 저장된 마지막 샘플 시각(없으면 마지막 저장 시각), `lastSequences` = 저장된 값(3절 규칙). 2절의 종료 장벽을 똑같이 따른다.
- 남아 있는 업로드 대기 항목은 지우지 않는다.

## 5. 추가: 업로드가 끝났음을 서버에 알린다 (`session:syncComplete`)

서버는 `session:syncComplete`(`{ clientSessionId 또는 sessionId, lastSequences }`)를 받으면 manifest를 비교하고, 일치하면 기다리지 않고 바로 최종 처리한다. 지금 iOS·Android 모두 보내지 않는다. 그래서 서버는 "폰에 아직 남은 것이 있는지"를 종료 요청 시점의 비교로만 판단한다.

요구: 한 세션의 큐가 완전히 빈 뒤(격리 항목 제외) 같은 `lastSequences`로 `session:syncComplete`를 한 번 보낸다. ACK의 `synchronized`가 false면 응답의 스트림별 `expected`/`server` 차이를 진단으로 남기고, 세션을 정리하지 않은 채 UI에 "미동기화"로 표시한다. 중복 전송은 서버가 안전하게 처리한다.

## 6. 조사: Stop 전에 센서가 먼저 멈춘 세션

`c441e46e`: 세션은 02:31:54Z에 끝났는데 모션 마지막 샘플은 02:31:14Z, 기압 마지막은 02:31:10Z다. 위치와 보행계는 02:31:51~52Z까지 있다. 폰이 보고한 개수와 서버 저장 개수가 같으므로 업로드 손실이 아니라 폰에서 약 40초간 모션·기압 수집이 멈췄다. 같은 세션은 배치 33개 중 24개가 역순으로 도착했다.

- 원인을 코드와 로그로 확인한다(모션 큐 정지, 배치 flush 타이머, ARKit과의 경합, 앱 상태 전환 등). 추측으로 고치지 않는다.
- 센서 콜백이 일정 시간(예: 모션 2초) 끊기면 진단 이벤트를 남긴다. `IOS_ANDROID_BASELINE_XCODE_PROMPT.md` 5절과 겹치면 그 작업을 쓴다.
- 원인을 찾지 못하면 재현 조건과 남긴 진단을 보고한다.

## 7. 하지 말 것

- 종료 요청을 보내기 위해 대기 항목을 지우거나 건너뛰지 않는다.
- 서버의 `FINISHED` 표시를 "업로드 완료"로 해석하지 않는다.
- 종료 요청, 진단 이벤트, `syncComplete`를 동시에 여러 개 겹쳐 보내지 않는다(지금처럼 한 번에 한 항목).
- 서버 계약을 바꾸지 않는다. 필요하면 변경 요청으로 보고한다.

## 8. 검증과 보고

자동 테스트(`CampusTrackerTests`, `PersistentUploadQueue`의 `directoryOverride`와 가짜 소켓 사용):

1. 수집 중 Stop: 큐 순서가 [센서 배치들, `SENSOR_STOPPED` ×4, 종료 요청]일 때 서버로 나가는 순서에서 종료 요청이 그 세션의 마지막 항목이고, 이어서 `syncComplete`가 나간다. 큐가 0이 된다.
2. 종료 ACK 직후 같은 세션에 진단 항목을 하나 더 넣어도 전송된다.
3. 진단 항목 하나가 재시도 불가로 격리되면: 종료 요청은 나가고, 세션은 정리되지 않으며, 대기 수는 0, 격리 수는 1로 보인다.
4. 보행계·기압 샘플이 없는 세션의 종료 요청 `lastSequences`에 `-1`이 들어간다.
5. "중단된 수집 종료"가 `interrupted: true` 종료 요청을 큐에 넣는다.
6. 종료 요청 전송 중 연결이 끊기고 앱이 재실행돼도 같은 순서로 이어진다(ACK 유실 시 중복 종료 요청은 서버가 멱등 처리).

실기기 확인(서버 API로):

1. Stop 직후 앱의 대기 수가 0으로 내려간다.
2. 그 세션의 `diagnostic-events`에 `SENSOR_STOPPED`가 센서 수만큼 있다.
3. 세션 상세의 `finalization.manifestSynchronized`가 `true`, `pendingOnDevice`가 `0`이다. 기압·보행계가 없는 짧은 세션에서도 마찬가지다.
4. 수집 중 앱을 강제 종료 → 재실행 → "중단된 수집 종료"를 하면 서버 세션이 ACTIVE로 남지 않고 `FINISHED`(`interrupted: true`)가 된다.
