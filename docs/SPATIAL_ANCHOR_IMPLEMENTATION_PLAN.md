# 캠퍼스 공간 필터와 신뢰 위치 앵커 적용 계획

작성일: 2026-10-02  
상태: 설계 문서. 애플리케이션 코드와 DB에는 아직 적용하지 않음.

## 1. 확정된 원칙

- 캠퍼스 다각형은 위치의 사용 가능 범위를 정한다. 경계선은 내부로 취급하고, 경계 밖 위치는 유효한 현재 위치와 앵커로 채택하지 않는다.
- 건물 다각형은 위치에 건물 정보를 붙이는 참고 자료로만 사용한다. 건물 밖이라는 이유로 실외라고 판단하지 않는다. 지하주차장처럼 도형에 없는 공간에서도 위치 추정을 계속한다.
- 건물 포함 여부로 GPS 가중치를 바꾸거나 좌표를 건물 안으로 이동시키지 않는다. 평면 도형만으로 입실이나 층을 확정하지 않는다.
- iOS 위치 중 정확도·시간적 연속성·이동 일관성이 충분한 관측만 절대 위치 앵커로 사용한다. Wi-Fi 활성화·연결 여부는 가중치 조건으로 사용하지 않는다.
- 원본 센서는 그대로 저장한다. 여기서 ‘무시’는 위치 추정과 유효 위치 제공에서 제외한다는 뜻이다. 원본 수신 성공 응답과 재전송 처리는 유지한다.
- 새 동작은 `fusion-v3`로 추가한다. 기존 결과와 비교한 뒤 실시간 기본 버전을 전환한다.

## 2. 확인한 현재 구조와 자료

현재 서버는 원본을 PostgreSQL/PostGIS에 저장한 뒤 비동기로 fusion을 실행한다. 실시간 기본 알고리즘은 설정으로 선택되며 현재 코드의 v2.1은 정확도가 낮은 위치도 일부 보정·방향 추정·재앵커 근거에 사용한다. 과거 세션 재처리와 서버 재시작 시 상태 복구 경로도 존재한다.

| 자료 | 확인 내용 |
| --- | --- |
| `campus_area.shp` | 2차원 Polygon 1개, 속성상 면적 약 57,226㎡ |
| `building.shp` | 2차원 Polygon 12개, 건물명 필드 존재, 이름 없는 도형 1개 |
| SHP 좌표계 | `.prj` 기준 KGD2002 / Central Belt 2010, EPSG:5186, 미터 단위 |
| 서버 위치 | WGS84 위경도, EPSG:4326. 저장 도형은 PointZ |

파일 구조와 속성은 확인했다. 도형 유효성, 건물 간 겹침, 캠퍼스 밖으로 나오는 건물, 실제 지도와의 정합성은 구현 첫 단계에서 확인한다. 캠퍼스 도형이 의도한 전체 운영 범위를 덮는지도 확인한다.

## 3. 지도 적재와 버전 관리

1. SHP와 부속 파일(`.shx`, `.dbf`, `.prj`, `.cpg`)을 프로젝트의 지도 원본 자료로 함께 보관한다. 데스크톱의 절대 경로에 운영 서버가 의존하지 않도록 한다.
2. 반복 실행 가능한 지도 가져오기 명령을 추가한다. 원본 파일 묶음의 해시, 원본 좌표계, 적재 시각을 기록한다.
3. `spatial_map_versions`, `campus_areas`, `campus_buildings` 테이블을 추가한다. 도형은 향후 확장을 고려해 MultiPolygon으로 정규화하고 공간 인덱스를 둔다.
4. 건물명과 독립적인 고정 건물 ID를 부여한다. 이름 없는 건물도 ID로 식별하며 화면에는 ‘이름 미등록’으로 표시한다. 향후 파일 순서가 바뀌어도 ID가 바뀌지 않도록 매핑을 보관한다.
5. 공간 판정은 EPSG:5186에서 수행한다. GPS의 경도·위도로 만든 점을 실제 좌표 변환한 뒤 포함 여부와 미터 단위 거리를 계산한다. PointZ를 판정할 때 높이는 제외한다. 지도 표시는 EPSG:4326으로 변환해 제공한다.
6. 유효하지 않은 도형은 사유를 출력하고 활성화를 중단한다. 임의로 경계를 수정해 활성화하지 않는다. 건물 겹침과 캠퍼스 밖 부분도 확인 목록으로 남긴다.
7. 활성 지도는 새 세션의 기본값으로 사용하고, 세션에는 지도 버전을 고정한다. 지도 데이터는 버전별로 보존한다. 다른 지도로 재처리할 때는 새 지도 버전의 실행 결과임을 명시한다.

알고리즘 버전·코드 revision·설정·지도 버전/해시를 실행 식별 정보에 포함한다. 기존 config hash, 결과 조회·교체 범위, 캐시 키를 함께 확장해 서로 다른 지도 결과가 섞이지 않게 한다. 과거 알고리즘은 지도 없는 기존 결과로 계속 조회할 수 있게 한다.

## 4. 위치 처리 흐름

```text
원본 수신 → 원본 저장 및 ACK
                  ↓
      측정 시각 순서 정리 + 공간 판정
                  ↓
        신뢰 위치 앵커 후보 검증
                  ↓
      앵커 + 걸음·방향·기압으로 추정
                  ↓
         추정 결과의 캠퍼스 판정
                  ↓
      유효 위치 + 참고용 건물 정보
                  ↓
          저장 / API / 실시간 표시
```

### 캠퍼스 입력 필터

- `ST_Covers`로 경계선까지 내부로 취급한다. 최초 버전에서는 캠퍼스 외곽에 자동 허용 버퍼를 추가하지 않는다.
- 외부 GPS는 `OUTSIDE_CAMPUS`로 기록한다. 초기화 후보, 위치 보정, 방향 추정, 안정 좌표 군집, 재앵커·발산 복구 근거에 들어가기 전에 차단한다.
- 점이 내부여도 오차 반경이 경계를 가로지르면 `BOUNDARY_UNCERTAIN`으로 기록하고 새 앵커로 채택하지 않는 보수적인 정책으로 시작한다. 정확도 반경은 절대 오차 보장이 아닌 추정치로 다룬다.
- 거부된 GPS도 시간 진행과 진단 이벤트에는 남긴다. 타임라인에서 단순 삭제해 출력 시각이나 재처리 결과가 달라지지 않도록 한다.
- 외부 GPS 한 점만으로 사용자의 실제 이탈을 확정하지 않는다. 해당 GPS를 제외한 뒤 기존 상대 추정은 불확실도 한도 안에서 계속할 수 있다.

### 추정 결과 필터

- 걸음 기반 이동이나 보정 결과가 캠퍼스 밖이면 유효 위치로 발행하지 않는다. 경계에 강제로 붙이거나 외부 후보를 다음 유효 상태의 기반으로 확정하지 않는다.
- 외부 후보와 제외 사유는 진단 이력에 남기고, 마지막 유효 위치는 원래 측정 시각으로 유지한다. 최신 위치처럼 타임스탬프만 갱신하지 않는다.
- 경계를 넘은 경우 위치 상태를 `REACQUIRE_REQUIRED`로 전환한다. 센서 누적값의 기준은 계속 관리하되, 재진입 시 그동안의 걸음 거리가 한 번에 적용되지 않게 한다.
- 새로운 내부 앵커가 확보되면 추정을 재개한다. 중단 전후 궤적은 별도 구간으로 표시해 빈 구간을 직선으로 연결하지 않는다.

## 5. 신뢰 위치 앵커 정책

다음 값은 첫 구현에 사용할 실험 시작값이다. 현장 검증 후 버전이 기록되는 설정으로 조정한다. 위치 갱신 빈도를 위성 수신률로 해석하지 않는다.

| 항목 | 초기 정책 |
| --- | --- |
| 수평 정확도 | 유효한 `horizontalAccuracy`, `0 < accuracy ≤ 5m` |
| 연속 관측 | 좋은 관측 최소 5개, 최소 3초 이상 지속 |
| 관측 간격 | 인접 관측 간격 최대 2초. 긴 공백이나 불량 관측이면 후보 연속성 초기화 |
| 관측 중복 | 같은 측정 시각의 중복 좌표는 연속 관측 수에 중복 산입하지 않음 |
| 정지 일관성 | 후보들이 중심 반경 5m 안에 모이는지 확인 |
| 이동 일관성 | 기존 보행 속도·물리적 점프 검사와 걸음 변화의 정합성을 확인. 이동 중 좌표를 한곳에 모이라고 요구하지 않음 |
| 공간 조건 | 캠퍼스 내부이며 경계 불확실 조건을 통과 |
| 시간 기준 | 업로드 도착 시각이 아닌 센서 측정 시각 |

### 초기화와 재보정

- 최초 신뢰 앵커가 생기기 전에는 `WAITING_FOR_ANCHOR` 상태로 둔다. 시간이 지났다는 이유로 낮은 품질의 위치로 초기화하지 않는다.
- 정지 중에는 후보 중심을, 이동 중에는 일관성이 확인된 최신 후보를 앵커로 사용한다. 이동 중 과거 좌표 평균을 현재 위치로 사용해 지연을 만들지 않는다.
- 이후에도 같은 품질 조건을 통과한 관측만 위치 보정에 사용한다. 유효한 추정 상태에서는 불확실도를 고려해 점진적으로 보정한다. 보정량에 제한을 두고 적용량을 기록한다.
- 중단된 상태나 큰 누적 오차에서 복귀할 때는 별도의 재획득 절차로 처리한다. 기존 추정과 멀다는 이유만으로 좋은 새 앵커를 영구 거부하지 않되, 단일 좌표만으로 크게 이동시키지도 않는다. 재획득은 새로운 궤적 구간으로 기록한다.
- 낮은 품질의 GPS는 수평 보정 가중치를 0으로 하고, 다른 경로를 통해 초기화나 방향·재앵커 근거로 우회 사용되지 않게 한다.

### 방향과 높이

- 위치 확보와 방향 확보를 별도로 관리한다. 위치만 확보한 상태는 `WAITING_FOR_HEADING`으로 표현한다.
- 좋은 위치의 신뢰 가능한 course 또는 오차보다 충분히 큰 두 앵커 사이 변위로 방향을 확보한다. 정지 위치만으로 방향을 만들어내지 않는다.
- 방향을 확보한 뒤 motion yaw 변화와 걸음 거리로 이동을 추정한다. 센서 공백 이후에는 방향 연속성을 재평가한다.
- 상대 높이는 기존 기압 기반 처리를 활용한다. GPS 수평 정확도가 좋다는 이유로 높이를 채택하지 않고, 수직 정확도와 기존 수직 점프 검사를 별도로 적용한다.
- 앵커 경과 시간·이동 거리·센서 공백에 따라 수평 불확실도를 증가시킨다. 불확실도가 초기 한도 20m를 넘으면 유효한 현재 위치 제공을 중단하고 재획득 상태로 전환한다. 이 값은 실제 오차를 보장하는 수치가 아니며 현장 기준점으로 보정한다.

정확도 좋은 관측이 드물면 초기화가 늦어지고 표시 가능한 궤적이 줄어들 수 있다. 현재 수집 데이터에서 앵커 확보 시간과 유지 비율을 확인한 뒤 기본 버전으로 전환한다.

## 6. 건물 참고 정보

- 유효한 보정 위치에 대해 건물 다각형 포함 여부만 계산한다.
- 결과에 `buildingId`, `buildingName`을 추가한다. 어떤 건물에도 겹치지 않으면 두 값은 null이다. null은 실외라는 뜻이 아니다.
- 불확실도 범위가 벽을 가로지르면 `buildingMatchStatus: BOUNDARY_UNCERTAIN`을 붙인다. 평면상 포함 결과 자체와 참고 정보의 불확실성을 함께 전달한다.
- 여러 건물과 겹치면 후보 ID 목록과 `AMBIGUOUS` 상태를 제공한다. 조회 순서에 따라 임의로 한 건물을 선택하지 않는다.
- 건물명은 ‘평면상 겹치는 건물’이라는 의미로 표시한다. 건물 출입 이벤트, 실내/실외 분류, 층수 판정은 이번 범위에 포함하지 않는다.

## 7. 저장·API·실시간 화면 변경

- 초기화 전에도 거부 이유를 확인할 수 있도록 GPS별 판단 이력을 원본과 별도로 저장한다. 세션·원본 sequence·실행 ID로 식별하고 공간 결과, 앵커 채택 여부, 거부 이유를 기록한다.
- 결과에는 지도 버전, 앵커 측정 시각, 마지막 앵커 이후 시간·거리, 추정 상태, 구간 ID, 건물 참고 정보를 추가한다.
- 좌표 출력이 없는 `WAITING_FOR_ANCHOR`와 `REACQUIRE_REQUIRED`도 전달할 수 있도록 상태 저장·조회와 실시간 상태 이벤트를 추가한다. 마지막 위치 한 행만으로 현재 상태를 복원하지 않는다.
- 원본 조회와 진단용 Raw 레이어는 유지한다. 기본 현재 위치와 유효 궤적은 v3 판정 결과를 사용하고, 제외된 원본은 진단용 표시로 구분한다.
- 실시간 방송, REST 조회, 재접속 snapshot, 서버 재시작 후 복원 모두 동일한 정책을 사용한다. 과거 업로드가 현재 마커나 상태를 과거로 되돌리지 않도록 측정 시각을 검사한다.
- 알고리즘 판정에는 현재 서버 시각을 사용하지 않는다. 과거 재처리에서도 측정 당시의 순서와 간격으로 판단한다. ‘지금 화면에 표시하기에 오래된 위치인가’는 표시 단계에서 따로 처리한다.
- 캠퍼스 경계와 건물 도형을 Preview에 표시한다. 대기·방향 미확보·상대 추정·재획득 필요 상태와 마지막 유효 위치 시각을 보여준다.
- 기존 iPhone 원본 업로드 필드로 우선 구현한다. Wi-Fi 상태 필드 추가는 필요하지 않다. 문서의 ‘GPS’ 표현에는 iOS Core Location 위치라는 의미를 명시한다.

## 8. 주요 변경 파일과 구현 순서

| 순서 | 변경 영역 | 작업 |
| --- | --- | --- |
| 1 | 지도 자료, `backend/scripts`, `backend/src/db/migrations` | 원본 보관, 지도 가져오기, 버전·도형 테이블과 검증 |
| 2 | 새 `backend/src/modules/spatial` | 공통 공간 판정, 지도 제공 API, 배치 처리 |
| 3 | `fusion-v3.engine.ts`, `fusion-state-v3.ts`, `fusion.config.ts`, `fusion.algorithms.ts` | 앵커 상태 관리, 입력·출력 필터, 새 알고리즘 등록 |
| 4 | `fusion.timeline.ts`, `fusion.service.ts`, `fusion.repository.ts`, 결과 DTO와 DB | 공간 결과 전달, 판단·상태 저장, 실행 식별 정보와 재처리 통합 |
| 5 | telemetry·session·realtime 모듈 | 원본 ACK 보존, 유효 최신 위치와 상태 복구, 이벤트 확장 |
| 6 | `frontend/src/api.ts`, `socket.ts`, `trajectory.ts`, `main.ts` | 지도 도형, 건물 정보, 상태, 궤적 구간과 진단 표시 |
| 7 | `docs/API_CONTRACT.md`, README, 설정 예시와 진단 도구 | 계약 문서, 운영 방법, 버전 비교 지표 |

공간 판정은 GPS 배치와 출력 후보에 대해 묶어서 수행한다. motion 샘플마다 DB에 질의하지 않는다. 실시간 처리와 재처리에서 같은 공간 판정 및 엔진을 사용한다. 지도 조회 실패나 활성 지도 누락 시 원본 수집은 계속하고, v3 결과는 오류 상태로 두어 공간 제약이 조용히 해제되지 않게 한다.

## 9. 검증과 완료 기준

### 자동 검증

- 캠퍼스 내부·경계·외부·구멍 영역, 좌표 변환 축 순서, 건물 중복과 미등록 이름을 검증한다.
- 외부 GPS가 초기화·방향·후보 군집·재앵커에 들어가지 않는지 확인한다.
- 단발성 좋은 위치, 연속 좋은 위치, 중복·역순·지연 업로드, 캐시 위치, 관측 공백을 검증한다.
- 위치만 확보된 상태, 방향 확보 후 보행, PDR 경계 이탈, 장시간 앵커 부재, 재진입 후 누적 걸음 기준을 확인한다.
- 건물 없는 공간에서도 같은 위치 정책이 적용되고, Wi-Fi 여부가 판단에 영향을 주지 않는지 확인한다.
- 동일한 원본·설정·지도 버전에서 최종 재처리와 상태 복구가 같은 결과를 내는지 확인한다. 정상 시간순 데이터는 배치 분할과 무관해야 한다. 실시간에 늦게 도착한 데이터는 기존 정책대로 최종 재처리에서 정정한다.
- 원본 보존·ACK 멱등성·기존 버전 조회와 진단 기능의 회귀를 확인한다.

### 현장 검증 및 전환

야외 시작 → 직선 보행 → 건물 내부 → 지하주차장 → 야외 복귀, 캠퍼스 경계 보행, 외부에서 시작해 진입하는 경로를 수집한다. 알려진 지점이나 확인 가능한 기준 위치와 비교하며, GPS 자체를 정답으로 사용하지 않는다.

첫 앵커 확보 시간, 유효 위치 제공 비율, 재획득 시간, 실제 기준점 오차, 제외 사유, 캠퍼스 밖 유효 출력 수를 v2.1과 비교한다. 캠퍼스 안에서 앵커를 잡지 못해 계속 대기하는 문제가 생기면 원인을 확인하고 설정을 조정한다.

완료 조건은 외부 위치가 유효 출력에 포함되지 않고, 낮은 품질 위치가 앵커에 영향을 주지 않으며, 건물 정보가 위치 채택 정책과 독립적으로 제공되는 것이다. 대표 현장 경로에서 위치 제공률과 기준점 오차를 확인한 뒤 `ACTIVE_FUSION_VERSION`을 v3로 전환한다. 비교 대상 시뮬레이터는 실제 캠퍼스 내부 좌표를 사용하도록 함께 정비한다.
